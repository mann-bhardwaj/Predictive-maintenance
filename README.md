# Industrial AI-Based Predictive Maintenance and Process Fault Detection

An end-to-end machine learning system that predicts equipment failure from
sensor data, diagnoses **which** fault is developing, flags abnormal operating
conditions without labels, and explains every decision in terms a maintenance
engineer recognises.

Built on the **AI4I 2020 Predictive Maintenance Dataset** (10,000 milling
machine cycles, UCI Machine Learning Repository).

---

## Headline results

Scored **once** on a held-out test set of 2,000 machines that no part of
training, model selection or threshold tuning ever touched:

| Metric | Value |
|---|---|
| **PR-AUC** (headline for a 3.4% event rate) | **0.877** |
| ROC-AUC | 0.969 |
| Recall — failures caught | **85.3%** (58 of 68) |
| Precision — alarms that were real | 70.7% |
| Recall at ≥90% precision | 76.5% |
| Maintenance cost avoided vs no system | **81.8%** |
| Brier score (probability calibration) | 0.0096 |

Supporting stages:

| Capability | Result |
|---|---|
| Fault-mode diagnosis (multi-label, 4 modes) | Top-1 diagnosis correct in **97.0%** of held-out failures |
| Unsupervised anomaly detection | ROC-AUC 0.892; **19× lift** over random inspection in the top 1% of the fleet |
| Model selection (5-fold CV PR-AUC) | Random forest **0.881 ± 0.025** · XGBoost 0.864 ± 0.031 · Logistic regression 0.473 ± 0.056 |

### The most interesting finding

Of the 10 failures the system missed, **eight are tool-wear failures and two
have no recorded cause at all.** It missed **zero** heat-dissipation, power, or
overstrain failures. The residual error is concentrated exactly where the
dataset itself is stochastic — the tool-wear rule has a random component, and
the two causeless rows are label noise that no sensor-driven model can predict.

## What this system does and does not claim

Being precise about this is the point of the project, not a disclaimer bolted on
at the end.

**It predicts failure state and diagnoses fault mode.** Given a cycle's sensor
readings, it estimates the probability of failure, decides whether that crosses
a cost-justified alarm threshold, names the most likely physical fault, and
explains the decision feature by feature.

**It does not predict remaining useful life, and RUL was not attempted.** RUL
regression needs run-to-failure trajectories — the same unit tracked over time
until it dies, so "cycles remaining" is observable. AI4I has no such structure:
each row is an independent snapshot with no unit identity carried across rows.
`Tool wear [min]` looks like a clock, but nothing links one row to the next.
Manufacturing an RUL target from the tool-wear threshold would give
`240 − tool_wear`, which is arithmetic dressed up as a model. A genuine RUL
study needs NASA C-MAPSS or comparable data.

## Three decisions that determine whether the numbers mean anything

### 1. Physics-informed features, but no rule-derived features

AI4I's labels were generated by deterministic threshold rules over the sensors.
A heat-dissipation failure, for instance, is recorded when the process/air
temperature differential falls below 8.6 K while rotational speed is below
1380 rpm.

It is therefore trivial to hand a model those thresholds as engineered flags and
report near-perfect scores — and equally trivial for a reviewer to spot that the
model was simply handed the answer key. So this project computes **physical
quantities only**:

| Derived quantity | Formula | Physical meaning |
|---|---|---|
| `mechanical_power_W` | `torque × speed × 2π/60` | Power delivered at the spindle |
| `temp_differential_K` | `process − air` | The gradient driving heat rejection |
| `wear_torque_strain_minNm` | `tool_wear × torque` | Load-weighted time in service |
| `torque_per_rpm` | `torque / speed` | Specific loading |
| `cooling_load_index` | `power / temp_differential` | Watts to shed per kelvin available |

**Deliberately absent:** no threshold comparisons, no type-specific limits, no
binary "at-risk" flags, no margin-to-threshold distances. The models discover
the operating limits from data. That is why the binary stage lands at PR-AUC
0.877 rather than 0.99.

**Where this still shows through, stated honestly:** the *fault-mode* stage
scores near-perfectly (PR-AUC 1.000 for power, 0.998 for heat dissipation).
That is structural, not an achievement — the fault taxonomy is *defined* in
terms of these physical quantities, so recovering a cut point on a feature the
model can see directly is not a hard inference problem. **The binary stage is
the honest measure of difficulty here.** Tool-wear failure, at 0.889, is the one
mode with genuine irreducible difficulty: fewest examples and a stochastic rule.

### 2. The alarm threshold is a business decision, made explicit

A classifier emits a probability; maintenance needs a yes/no. For a 3.4% event
rate, 0.5 is close to never correct.

The assumption used: **a missed failure costs 10× an unnecessary inspection.**
Both true and false positives incur the same inspection cost, so it cancels and
the objective reduces to `cost = 10 × missed + 1 × false alarms`. The threshold
minimising that cost is **0.251**, selected on out-of-fold training predictions
and never on the test set.

Because the 10:1 ratio was *chosen* rather than measured, its influence is
quantified rather than hidden:

| Cost ratio (miss : false alarm) | Threshold | Precision | Recall | False alarms | Missed |
|---|---|---|---|---|---|
| 5:1 | 0.321 | 83.4% | 83.4% | 45 | 45 |
| **10:1** *(used)* | **0.251** | **72.5%** | **85.6%** | **88** | **39** |
| 20:1 | 0.126 | 49.1% | 88.9% | 250 | 30 |
| 50:1 | 0.054 | 31.6% | 94.5% | 555 | 15 |

*(out-of-fold figures on 8,000 training rows)*

A maintenance manager picks the row. The model supplies the trade-off curve.

### 3. Class imbalance: weights, not synthetic data

339 failures in 10,000 rows. Handled with `class_weight='balanced'` and
`scale_pos_weight`, **not** SMOTE. Synthetic sensor readings can be physically
impossible — a torque/speed pair off the constant-power hyperbola describes a
machine that cannot exist — and oversampling must never touch a validation fold.
Class weighting has neither problem.

## Honest limitations

- **2.7% label-noise floor.** 9 of 339 failures carry no physical fault flag,
  and 18 of the 19 `RNF` (random failure) flags sit on cycles that completed
  fine. Identical sensor readings elsewhere are labelled healthy, so these rows
  are unpredictable by construction. Recall should be judged against that
  ceiling, not against 100%.
- **`RNF` is kept in the binary target but excluded from fault diagnosis.**
  Operationally a failure is a failure; statistically a random failure has no
  sensor signature to learn.
- **Fault diagnosis is conditional.** It assumes a failure has been flagged and
  covers only the four physically-driven modes.
- **The dataset is synthetic.** Realistic and standard as a benchmark, but real
  plant data brings sensor drift, missing intervals, and regime changes that
  none of this exercises.
- **Small mode populations.** Tool-wear failure has 36 training examples, so its
  cross-validated score carries real variance.
- **The anomaly detector is deliberately weaker.** Fitted on healthy rows only,
  with no label access, it exists to cover fault types the classifier has never
  seen — not to beat it.

## Environment setup

This project is validated on Python 3.11.x. It is not recommended to run it on Python 3.14 in its current state because XGBoost on macOS requires the OpenMP runtime (`libomp`).

```bash
# macOS
brew install libomp

# then create a clean environment and install dependencies
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Running it

```bash
# Train everything: ~70 seconds. Writes models/, reports/figures/, reports/metrics/
python run_pipeline.py

# Interactive dashboard
streamlit run app/streamlit_app.py

# Or read the notebooks in order
jupyter lab notebooks/
```

The pipeline is deterministic (`random_state=42` throughout), so a fresh run
reproduces every number in this README exactly.

### The dashboard

Three tabs:

1. **Single machine** — sliders for the six sensor inputs, plus preset fault
   scenarios. Returns failure probability against the threshold, a per-mode
   fault diagnosis, an anomaly score with a fleet percentile, and a live SHAP
   explanation with a plain-language summary.
2. **Fleet scoring** — upload a CSV (or score the held-out split) and get a
   ranked inspection-priority list with a suggested cause per machine,
   downloadable as CSV.
3. **Model card** — training configuration, cross-validated and held-out
   metrics, the operating-point rule, and the known limitations above.

## Methodology

| Stage | What was done |
|---|---|
| **1 — Data and understanding** | Schema audit; 0 missing values; every sensor's physical role documented; label integrity audited, surfacing the RNF anomaly, 9 causeless failures, and 23 co-occurring modes; noise floor quantified |
| **2 — EDA** | Outlier analysis (nothing removed — outliers are the high-risk population); healthy vs failed distributions; correlation structure (torque/speed ≈ −0.88, a constant-power spindle); the two-corner failure geometry in the operating envelope; wear hazard curve |
| **3 — Baseline ML** | Logistic regression → random forest → XGBoost; stratified 80/20 split; 5-fold stratified CV with the full pipeline refitted inside every fold; cost-driven threshold from out-of-fold predictions |
| **4 — Anomaly detection** | Isolation Forest fitted on healthy training rows only; evaluated against labels afterwards; framed as inspection lift |
| **5 — Predictive maintenance** | Multi-label fault-mode diagnosis, one binary head per mode, conditional on failure; per-mode CV; composed into a work-order list |
| **6 — Explainability** | Global SHAP (validates the feature engineering); local SHAP for a caught failure, a false alarm and a missed failure; calibration check |

### Leakage controls

- The test set is scored **exactly once**, at the very end.
- The decision threshold is tuned only on out-of-fold training predictions.
- Imputation, scaling and one-hot encoding are refitted **inside** every CV
  fold, so no validation-fold statistic reaches its own training fold.
- The anomaly detector never sees a label during fitting.
- `UDI` and `Product ID` are excluded as identifiers — `UDI` is a row counter
  and `Product ID` encodes the machine type that is already a feature.

### A detail worth knowing about SHAP units

`TreeExplainer` reports contributions in whatever space the model's raw output
occupies: **probability** for a random forest (it averages leaf class
frequencies), **log-odds** for gradient boosting (the additive margin before the
logistic link). The explainer detects which model it holds and labels every
figure accordingly, so `+0.20` is never read as the wrong quantity.

## Dataset

**AI4I 2020 Predictive Maintenance Dataset** — 10,000 rows, 14 columns.
Synthetic but constructed to reflect real industrial predictive-maintenance
data. Source: UCI Machine Learning Repository
(<https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset>).

Verified on load: 10,000 rows, 0 missing values, 339 failures, and mode counts
TWF 46 / HDF 115 / PWF 95 / OSF 98 / RNF 19 — matching the published dataset
exactly.
